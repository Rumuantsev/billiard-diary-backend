# Billiard Diary Backend - handoff context

Этот файл создан как "свертка" контекста для продолжения работы в новом чате/аккаунте.

## 1. Что это за проект

Проект: дневник тренировок по бильярду.

Основная идея:

- тренер ведет спортсменов;
- спортсмены могут быть объединены в группы;
- тренер создает упражнения;
- упражнения можно раскладывать по папкам;
- тренер проводит групповые тренировки;
- внутри групповой тренировки есть индивидуальные тренировки спортсменов;
- внутри тренировки спортсмена есть элементы тренировки: упражнение, порядок, план попыток, фактические попытки, успешные попытки, статус;
- фиксируется посещаемость;
- могут быть комментарии к групповой тренировке, тренировке спортсмена или элементу тренировки.

Ключевая продуктовая цель: дать тренеру не только CRUD, но и понимание динамики спортсменов: посещаемость, объем работы, прогресс по упражнениям.

## 6. Прототип аналитики: история решений

Сначала была добавлена статичная страница аналитики как "карта возможностей", максимально широкая и даже громоздкая.

Потом пользователь уточнил:

- статусы тренировок не важны;
- статистика упражнений как самостоятельная сущность не важна;
- мы тренируем не упражнения, а спортсменов;
- главное:
  - посещаемость спортсменов;
  - сколько упражнений успевают за тренировку;
  - прогресс по конкретным упражнениям.

Потом пользователь сам переделал `front-prototypes/withGroups/coach/analytics.html`.

Последняя оценка этого файла:

- функционал прототипа вырос;
- появилась интерактивная аналитическая витрина;
- есть вкладки, графики, фильтры, mock data;
- стиль не совпадает с остальным прототипом, но это сейчас не главное;
- основной риск: прогресс местами снова превращается в аналитику упражнений, а не спортсменов;
- при реальных 30 спортсменах и 100 упражнениях нужно мыслить через пару `спортсмен + упражнение + период`;
- важно не показывать все 3000 комбинаций без фильтров;
- важны сортировки, фильтры, пагинация, поиск, статусы достаточности данных.

## 7. Текущая позиция пользователя по аналитике

Пользователь отказался от полноценной рекомендательной системы для MVP.

Он осознанно выбирает более простой вариант:

> "Вот 30 спортсменов, 100 упражнений, проценты, графики, разбирайся."

То есть на MVP нужна не умная рекомендательная система, а аналитическая витрина.

Важно: не проектировать сразу сложный AI/рекомендательный механизм. Нужны данные, таблицы, графики, фильтры, сортировки, срезы.

## 8. Главная аналитическая единица

Ключевая единица для будущей аналитики:

```text
спортсмен + упражнение + период
```

Именно вокруг нее строится прогресс.

Пример:

```text
Алексей / Дальний в угол / май 2026
выполнений: 8
попыток: 86
успешных: 49
успешность: 56.98%
первые 3 выполнения: 42%
последние 3 выполнения: 61%
дельта: +19 п.п.
качество данных: достаточно
```

## 9. Что важно для MVP аналитики

Разделы:

### 9.1. Обзор

Ответ на вопрос:

> Что происходит в выбранный период?

Метрики:

- количество спортсменов;
- количество групп;
- количество тренировок;
- средняя посещаемость;
- среднее количество упражнений за тренировку;
- всего попыток;
- всего успешных попыток;
- общий процент успешности;
- активные спортсмены;
- спортсмены без тренировок;
- упражнения, которые выполнялись.

### 9.2. Посещаемость

Срезы:

- по спортсменам;
- по группам;
- по дням;
- по месяцам;
- текущий период vs прошлый период.

Таблица:

```text
спортсмен | тренировок всего | посетил | пропустил | % посещаемости | последняя тренировка
```

### 9.3. Объем работы

Смысл: сколько спортсмен реально делает.

Метрики:

- тренировок посетил;
- упражнений всего;
- среднее упражнений за тренировку;
- попыток всего;
- среднее попыток за тренировку;
- динамика по времени.

Таблица:

```text
спортсмен | тренировок | упражнений всего | ср. упражнений за тренировку | попыток всего | ср. попыток
```

### 9.4. Прогресс по упражнениям

Главная таблица:

```text
спортсмен | упражнение | выполнений | попыток | успешных | % успеха | первые выполнения | последние выполнения | дельта
```

Фильтры:

- период;
- группа;
- спортсмен;
- упражнение;
- минимум выполнений;
- минимум попыток;
- только выполнявшиеся;
- только с ростом;
- только со спадом;
- только мало данных.

## 10. Важная идея: качество/достаточность данных

Даже без рекомендательной системы нужно не делать ложных выводов.

Пороговая логика:

```text
0 выполнений: нет данных
1-2 выполнения: мало данных
3-4 выполнения: предварительно
5+ выполнений: можно оценивать
8+ выполнений: устойчивый тренд
```

Это можно назвать `dataQuality`.

Пример значений:

- `no_data`
- `not_enough_data`
- `preliminary`
- `enough`
- `strong`

Это не рекомендация, а честное описание надежности аналитики.

## 11. Как считать прогресс без рекомендательной системы

Простой вариант:

1. Взять все выполнения конкретного упражнения конкретным спортсменом за период.
2. Отсортировать по дате.
3. Если выполнений мало, вернуть `not_enough_data`.
4. Сравнить первые N выполнений и последние N выполнений.

Например:

```text
первые 3 выполнения: 42%
последние 3 выполнения: 61%
дельта: +19 п.п.
```

Можно классифицировать:

- `growth`
- `decline`
- `stable`
- `not_enough_data`

Это все еще не рекомендательная система.

## 12. Архитектурные варианты аналитики

Пользователь просил мыслить широко, вплоть до микросервиса и витрины данных.

### Вариант 1. Аналитика прямо в текущем backend

Отдельный модуль:

```text
src/routes/analytics.route.js
src/controllers/analytics.controller.js
src/services/analytics.service.js
src/repositories/analytics.repository.js
```

Плюсы:

- быстро;
- хорошо для MVP;
- меньше инфраструктуры;
- проще защищать.

Минусы:

- тяжелые SQL могут нагружать основной backend;
- аналитическая логика живет в монолите.

Рекомендация: для MVP начать именно так.

### Вариант 2. SQL views

Создать представления:

```text
analytics_attendance_view
analytics_training_volume_view
analytics_exercise_progress_view
analytics_athlete_period_summary_view
```

Плюсы:

- логика ближе к данным;
- API проще;
- переиспользуемые расчеты.

Минусы:

- параметризованные периоды во views не всегда удобны;
- сложные views могут стать тяжелыми.

### Вариант 3. Materialized views

Предрассчитанные витрины:

```text
analytics_athlete_exercise_daily
analytics_athlete_exercise_monthly
analytics_attendance_monthly
analytics_group_monthly
```

Плюсы:

- быстро читать;
- хорошо для отчетов;
- снижает нагрузку.

Минусы:

- нужно обновление;
- проблема актуальности;
- сложнее поддержка.

### Вариант 4. Отдельная analytics schema в той же PostgreSQL

Например:

```text
app.*
analytics.*
```

Плюсы:

- логическое разделение;
- без отдельного микросервиса;
- можно потом вынести.

### Вариант 5. Отдельный analytics service

Целевая архитектура:

```text
Основной backend
  -> events / cron / SQL sync
Analytics service
  -> analytics DB / data mart
Frontend dashboard
```

Плюсы:

- чистое разделение;
- аналитика не тормозит основной backend;
- можно масштабировать отдельно;
- можно подключать BI.

Минусы:

- сильно сложнее;
- не нужно для MVP.

### Вариант 6. Data mart / витрина данных

Плоская таблица фактов:

```text
analytics_training_item_fact
```

Одна строка = одно выполнение упражнения спортсменом.

Поля:

```text
date
coach_id
group_id
athlete_id
athlete_name
exercise_id
exercise_name
training_id
attempts
successes
success_rate
status
```

Это очень удобно для графиков, таблиц, отчетов, BI.

## 13. Практическая рекомендация по архитектуре

Начать так:

```text
Этап 1: analytics module внутри текущего backend
Этап 2: SQL views для повторяющихся расчетов
Этап 3: analytics schema / data mart в той же PostgreSQL
Этап 4: отдельный analytics service только при реальной необходимости
```

То есть не делать микросервис сейчас, но проектировать модуль так, чтобы его можно было вынести.

## 16. Важные UX/product мысли по аналитике

Даже если MVP - это "разбирайся сам", инструмент должен быть управляемым:

- не показывать все 3000 строк сразу;
- обязательно фильтры;
- обязательно сортировки;
- обязательно поиск по спортсмену и упражнению;
- таблицы должны иметь пагинацию;
- проценты всегда показывать вместе с объемом данных;
- не делать главный экран рейтингом "лучший/худший";
- сравнивать спортсмена с самим собой в прошлом периоде честнее, чем сравнивать спортсменов между собой;
- "нет данных" и "мало данных" - это важные аналитические состояния, а не пустота.

## 17. Что не стоит делать сейчас

Для MVP не стоит:

- делать полноценную рекомендательную систему;
- делать AI-интерпретацию;
- сразу выносить аналитику в микросервис;
- строить отдельное хранилище;
- делать сложный ETL;
- превращать аналитику в красивый, но бесполезный дашборд без таблиц и фильтров.

## 18. Что стоит делать следующим

## 20. Последний актуальный контекст

Последняя тема: проектирование аналитики без рекомендательной системы.

Позиция:

- API пока можно не проектировать окончательно, но архитектурно думать уже надо;

> Продолжаем проектировать analytics endpoints или сначала приводим `analytics.html` к более реалистичной структуре MVP?
